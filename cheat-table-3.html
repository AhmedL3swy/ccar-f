Domain 3

Claude Code Configuration & Workflows

20% of exam

Configure Claude Code for productive, consistent and scalable development workflows.

3.1

CLAUDE.md hierarchy, scoping & modular organisation

Organise instructions with the right scope and structure.

Hierarchy & scope

User-level
~/.claude/CLAUDE.md
  • Personal instructions
  • Not shared with the team
  • Applies to all your projects
Project-level
CLAUDE.md or .claude/CLAUDE.md
  • Shared via version control
  • Project-specific context
  • Team standards
Directory-level
CLAUDE.md
  • Applies to a subdirectory
  • Adds detail for specific modules
  • Useful for packages / modules

Modular organisation

  • Use @import (e.g. @path/to/standards.md) to include external standards (testing, API rules).
  • Keep topic files in .claude/rules/ (e.g. testing.md).

Avoid

  • Putting team or project standards only in a user-level CLAUDE.md: teammates never receive them.
3.2

Custom slash commands & skills

Reusable workflows with the right scope and configuration.

Slash commands

Project
.claude/commands/
  • Shared via version control
  • Team-wide availability
Personal
~/.claude/commands/
  • Personal use only
  • Not shared

Skills

Project
.claude/skills/<name>/SKILL.md
  • Reusable workflows
  • On-demand (not always loaded)
  • Frontmatter config
Personal
~/.claude/skills/
  • Personal variants
  • Use distinct names
  • Not shared

Frontmatter options (SKILL.md)

---
name: my-skill
context: fork
allowed-tools: ["Read", "Grep"]
argument-hint: "<description>"
---
  • context: fork → isolates verbose skill output from the main conversation.
  • allowed-tools → restricts tool access.
  • argument-hint → guides required parameters.

Rule of thumb

Skills = on-demand, task-specific workflows. CLAUDE.md = always-loaded general guidance.

3.3

Path-specific rules for conditional loading

Apply rules only to matching files to cut irrelevant context.

How it works

  • Put rule files in .claude/rules/ with YAML frontmatter.
  • Use glob patterns in the paths field.
  • Rules load only when Claude works on matching files.
  • Reduces irrelevant context and token usage.

Example

---
paths:
  - "**/*.test.tsx"
  - "src/api/**"
---

Use glob patterns for broad conventions

  • Patterns like **/*.test.tsx work when conventions span many directories.

Avoid

  • Relying only on directory-level CLAUDE.md when you need file-type-specific rules.
3.4

Plan mode vs direct execution

Choose the mode by task complexity.

Plan mode

  • Complex tasks touching many files
  • Architecture decisions
  • Migrations and large-scale changes
  • Several valid approaches
  • Explore safely before making changes

Example use cases

  • Library migration
  • Microservice restructuring
  • Changes affecting many files
  • Evaluating different approaches

Direct execution

  • Simple, well-scoped changes
  • Small edits or single-function fixes
  • Clear requirements
  • Add a validation check or minor bug fix

Example use cases

  • Fix a single bug
  • Add a small feature
  • Update a few lines

Explore subagent

Use the Explore subagent to isolate verbose discovery output and keep the main conversation focused.

3.5

Iterative refinement techniques

Structured techniques that improve results over time.

  1. Provide 2–3 concrete input/output examplesWhen natural-language descriptions are ambiguous.
  2. Write tests firstCover expected behaviour, edge cases and performance.
  3. Share test failures with ClaudeIterate using the actual failures to guide improvements.
  4. Use the interview patternLet Claude ask questions to surface missing requirements and failure modes.
  5. Address interacting issues togetherFix related issues in a single pass; handle independent issues sequentially.
3.6

CI/CD integration

Run Claude Code in automated pipelines with structured output.

Non-interactive executionUse -p (or --print) to run Claude Code in CI without interactive input.
Independent reviewUse a separate review instance instead of reviewing in the generation session.
Structured outputUse --output-format json and --json-schema for machine-readable, constrained output.
On rerunsInclude previous findings and report only new or unresolved issues to avoid duplicate comments.
Project contextCLAUDE.md gives CI the testing standards, fixtures and review criteria.
Existing tests / fixturesProvide existing test files in context to avoid generating duplicate tests.

Key takeaways

  1. CLAUDE.md = always-loaded general standards.
  2. Skills = on-demand, task-specific workflows.
  3. Plan mode = complex changes and exploration.
  4. Direct execution = simple, well-scoped changes.
  5. .claude/rules/ with glob paths = rules load only for matching files.
  6. -p runs Claude Code non-interactively in CI.
  7. JSON Schema guarantees structured output, not semantic truth.
  8. Use a separate instance for independent reviews.
  9. Provide examples, use tests and iterate with feedback.
  10. Include previous findings on reruns to avoid duplicates.

Skill frontmatter fields that are easy to confuse

FieldWhat it controlsWhat it does not do
context: forkExecutes the skill inside a separate-context subagent and returns just a summaryDoes not change who may invoke the skill
allowed-toolsPre-approves listed tools for the invoking turn onlyDoes not remove unlisted tools; they still prompt
disallowed-toolsRemoves listed tools while the skill is activeDoes not pre-approve anything
disable-model-invocation: trueOnly a person typing /name can start the skillDoes not keep output out of the main conversation
user-invocable: falseRemoves the skill from the / menu; Claude alone can invoke itDoes not isolate context
