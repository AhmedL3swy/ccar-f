3.1

CLAUDE.md hierarchy, scoping & modular organisation

5

Organise instructions with the right scope and structure.

Hierarchy & scope

User-level
~/.claude/CLAUDE.md
  • Personal instructions
  • Not shared with the team
  • Applies to all your projects
Project-level
CLAUDE.md or .claude/CLAUDE.md
  • Shared via version control
  • Project-specific context
  • Team standards
Directory-level
CLAUDE.md
  • Applies to a subdirectory
  • Adds detail for specific modules
  • Useful for packages / modules

Modular organisation

  • Use @import (e.g. @path/to/standards.md) to include external standards (testing, API rules).
  • Keep topic files in .claude/rules/ (e.g. testing.md).

Avoid

  • Putting team or project standards only in a user-level CLAUDE.md: teammates never receive them.

Custom slash commands & skills

  • Team-wide availability

~/.claude/commands/
  • Personal use only
  • Not shared

Skills

Project
.claude/skills/<name>/SKILL.md
  • Reusable workflows
  • On-demand (not always loaded)
  • Frontmatter config
Personal
~/.claude/skills/
  • Personal variants
  • Use distinct names
  • Not shared

Frontmatter options (SKILL.md)

---
name: my-skill
context: fork
allowed-tools: ["Read", "Grep"]
argument-hint: "<description>"
---
  • context: fork → isolates verbose skill output from the main conversation.
  • allowed-tools → restricts tool access.
  • argument-hint → guides required parameters.

Rule of thumb

Skills = on-demand, task-specific workflows. CLAUDE.md = always-loaded general guidance.

3.3

Path-specific rules for conditional loading

5

Apply rules only to matching files to cut irrelevant context.

How it works

  • Put rule files in .claude/rules/ with YAML frontmatter.
  • Use glob patterns in the paths field.
  • Rules load only when Claude works on matching files.
  • Reduces irrelevant context and token usage.

Example

---
paths:
  - "**/*.test.tsx"
  - "src/api/**"
---

Use glob patterns for broad conventions

  • Patterns like **/*.test.tsx work when conventions span many directories.

Avoid

  • Relying only on directory-level CLAUDE.md when you need file-type-specific rules.

Plan mode vs direct execution

6

Choose the mode by task complexity.

Plan mode

  • Complex tasks touching many files
  • Architecture decisions
  • Migrations and large-scale changes
  • Several valid approaches
  • Explore safely before making changes

Example use cases

  • Library migration
  • Microservice restructuring
  • Changes affecting many files
  • Evaluating different approaches

Direct execution

  • Simple, well-scoped changes
  • Small edits or single-function fixes
  • Clear requirements
  • Add a validation check or minor bug fix

Example use cases

  • Fix a single bug
  • Add a small feature
  • Update a few lines

3.5

Iterative refinement techniques

6

Structured techniques that improve results over time.

  1. Provide 2–3 concrete input/output examplesWhen natural-language descriptions are ambiguous.
  2. Write tests firstCover expected behaviour, edge cases and performance.
  3. Share test failures with ClaudeIterate using the actual failures to guide improvements.
  4. Use the interview patternLet Claude ask questions to surface missing requirements and failure modes.
  5. Address interacting issues togetherFix related issues in a single pass; handle independent issues sequentially.

Key takeaways

  1. CLAUDE.md = always-loaded general standards.
  2. Skills = on-demand, task-specific workflows.
  3. Plan mode = complex changes and exploration.
  4. Direct execution = simple, well-scoped changes.
  5. .claude/rules/ with glob paths = rules load only for matching files.
  6. -p runs Claude Code non-interactively in CI.
  7. JSON Schema guarantees structured output, not semantic truth.
  8. Use a separate instance for independent reviews.
  9. Provide examples, use tests and iterate with feedback.
  10. Include previous findings on reruns to avoid duplicates.

Key factsمعلومات مهمة 10

  • ~/.claude/CLAUDE.md User-level instructions that load in every project on your machine and are never committed.
    ~/.claude/CLAUDE.md تعليمات على مستوى المستخدم بتتحمّل في كل مشروع على جهازك وعمرها ما بتتعمل كوميت.
  • ./CLAUDE.md or ./.claude/CLAUDE.md Project-level instructions shared with the team through source control.
    ./CLAUDE.md أو ./.claude/CLAUDE.md تعليمات على مستوى المشروع بتتشارك مع الفريق عن طريق نظام التحكم في النسخ.
  • ./CLAUDE.local.md Personal instructions for one project (e.g. your sandbox URLs); add it to .gitignore.
    ./CLAUDE.local.md تعليمات شخصية لمشروع واحد (زي روابط URL بتاعة بيئة التجربة عندك)؛ ضيفه في .gitignore.

    مسارات ملف CLAUDE.md بتاع السياسة المُدارة على macOS /Library/Application Support/ClaudeCode/CLAUDE.md؛ وعلى Linux وWSL /etc/claude-code/CLAUDE.md؛ وعلى Windows C:\Program Files\ClaudeCode\CLAUDE.md.
  • managed-settings.json Enforced managed settings that cannot be overridden by personal settings or --settings (few exceptions); can carry instruction text in claudeMd and block tools with permissions.deny or enable sandboxing.
    managed-settings.json إعدادات مُدارة بتتفرض ومينفعش الإعدادات الشخصية أو --settings يلغوها (إلا استثناءات قليلة)؛ وممكن تشيل نص تعليمات في claudeMd، وتمنع أدوات بـ permissions.deny أو تفعّل تشغيل الأدوات في بيئة معزولة.

    /memory بيعرض ملفات CLAUDE.md وملفات الذاكرة اللي في نطاق الجلسة، ويخليك تفتحها وتعدّلها.

    ~/.claude/projects/<project>/memory/ المكان اللي بتتخزن فيه ملاحظات الذاكرة التلقائية؛ متعملهاش كوميت، فالنسخة الجديدة من المستودع مش بتاخدها.
  • @path / @~/... Import syntax inside CLAUDE.md that loads the referenced file at launch; external imports require approval.
    @path / @~/... صيغة الاستيراد جوه ملف CLAUDE.md اللي بتحمّل الملف المذكور أول ما تفتح؛ والاستيراد من برا المشروع محتاج موافقة.
  • About 200 lines Recommended maximum size for each CLAUDE.md file.
    حوالي 200 سطر أقصى حجم منصوح بيه لكل ملف CLAUDE.md.

Key factsمعلومات مهمة 10

  • .claude/commands/<name>.md Command file format; the command name is the filename, and subfolders become : prefixes such as /frontend:component.

    argument-hint تلميح في الإكمال التلقائي للمُدخل المتوقع؛ في Claude Code بس، وأماكن رفع المهارات بترفضه لأنها بتقبل name وdescription وlicense وcompatibility وmetadata وallowed-tools بس.

Key factsمعلومات مهمة 9

  • paths The only frontmatter field for rule files; a YAML list or comma-separated string of globs, and omitting it makes the rule apply everywhere.
    paths الحقل الوحيد في ترويسة ملفات القواعد؛ عبارة عن قائمة YAML أو نص من أنماط المسارات مفصولة بفواصل، ولو شيلته القاعدة بتتطبق في كل حتة.
  • * Matches within a single directory level only.
    * بتطابق جوه مستوى مجلد واحد بس.
  • ** Matches across any number of nested directories.
    ** بتطابق عبر أي عدد من المجلدات المتداخلة.
  • **/*.ts TypeScript files in any directory of the repo.
    **/*.ts ملفات TypeScript في أي مجلد في المستودع.
  • *.md Markdown files in the project root only.
    *.md ملفات Markdown اللي في جذر المشروع بس.
  • src/**/*.{ts,tsx} Every .ts or .tsx file inside src/, however deeply nested.
    src/**/*.{ts,tsx} أي ملف .ts أو .tsx جوه src/، مهما كان متداخل لتحت.
  • src/api/**/*.ts Only TypeScript files inside src/api/, nested to any level; nothing elsewhere in src/ matches.
    src/api/**/*.ts ملفات TypeScript اللي جوه src/api/ بس، في أي مستوى تداخل؛ ومفيش أي حاجة تانية في src/ بتطابق.
  • terraform/* vs terraform/**/* The first matches only files directly inside terraform/; the second covers the whole tree.
    terraform/* مقابل terraform/**/* الأول بيطابق الملفات اللي جوه terraform/ على طول بس؛ والتاني بيغطي الشجرة كلها.
  • **/*.test.tsx Component test files wherever they live, including __tests__ folders and a root tests/ folder.
    **/*.test.tsx ملفات اختبارات المكوّنات في أي مكان موجودة فيه، ومن ضمنها مجلدات __tests__ ومجلد tests/ اللي في الجذر.

  • Path-scoped rule A .claude/rules/ file with paths globs that loads only when Claude works with a matching file.

توقّع إن المهارة الشخصية هي اللي هتشتغل؛ وادّي النسخ الشخصية أسماء مختلفة عشان مهارة الفريق تفضل محتفظة باسمها.

allowed-tools only pre-approves the listed tools for the invoking turn; Bash stays in Claude's tool pool, so a destructive command would stop at a permission prompt rather than being impossible.
allowed-tools بيدّي موافقة مسبقة للأدوات اللي فيه في الدور اللي نادى المهارة وبس؛ وBash بيفضل موجود في مجموعة الأدوات المتاحة لـ Claude، فأي أمر مدمّر هيقف عند طلب الإذن، مش هيبقى مستحيل.

Setting disable-model-invocation: true is how you stop a skill's exploratory output from landing in the main conversation.

That field only prevents Claude from triggering the skill by itself; when a person runs it, everything it produces still lands in the main conversation.

Set context: fork so the skill runs in a subagent and only its summary comes back.
حط context: fork عشان المهارة تشتغل في وكيل فرعي ويرجع الملخص بتاعها بس.
When two skills have the same name, Claude Code either combines them or raises a naming-conflict error.
لما مهارتين يبقى ليهم نفس الاسم، Claude Code يا إما بيدمجهم يا إما بيطلّع خطأ إن فيه تعارض في الأسماء.
Exactly one definition runs according to a fixed override order; there is no merge and no conflict error.
تعريف واحد بس اللي بيشتغل على حسب ترتيب أولوية ثابت؛ مفيش دمج ومفيش خطأ تعارض.
Apply enterprise over personal over project (and skill over command file) to decide which runs.
طبّق الترتيب: المؤسسة فوق الشخصي فوق المشروع (والمهارة فوق ملف الأمر) عشان تعرف مين اللي هيشتغل.
A skill's context is kept separate if you set user-invocable: false or add a paths field.
سياق المهارة بيتفصل لو حطيت user-invocable: false أو ضفت حقل paths.
Those fields control who can invoke the skill or when it loads automatically, not where it runs, so output still enters the main session.
الحقول دي بتتحكم في مين يقدر ينادي المهارة أو إمتى تتحمّل لوحدها، مش في هي بتشتغل فين، فالمخرجات برضه بتدخل الجلسة الأساسية.
Only context: fork isolates the run.
context: fork بس هو اللي بيعزل التشغيل.
How the exam tests this
  • When names collide, one skill wins by a set precedence, and a personal skill outranks a project skill. Nothing gets merged and no conflict error appears, so eliminate any answer saying the project skill always takes precedence.
  • Pick context: fork whenever a question asks how to stop a skill's verbose or exploratory output from reaching the main session so that only the result comes back. Answers built on disable-model-invocation, user-invocable or paths are distractors: those fields control invocation or loading, not context.

How the exam tests this
  • Rule frontmatter has exactly one field, paths, so an answer that otherwise looks right but uses some other key, such as include:, can be ruled out from that key alone.

3.4 Determine when to use plan mode vs direct execution

Plan mode never prompts for read-only commands because those commands skip approval in all permission modes.

Reads pass in plan mode because that mode permits them, not because of a global exemption; with permissions.blockReadsOutsideWorkingDirectories on, out-of-directory reads still prompt even in auto and bypassPermissions, and explicit ask rules prompt in every mode.
القراية بتعدّي في وضع التخطيط عشان الوضع ده بيسمح بيها، مش عشان فيه استثناء عام؛ ولو permissions.blockReadsOutsideWorkingDirectories شغال، القراية برا مجلد الشغل برضه بتطلب موافقة حتى في auto وbypassPermissions، وقواعد «اسأل» الصريحة بتطلب موافقة في كل الأوضاع.
Plan mode allows reads by design and holds edits until the plan is approved.
وضع التخطيط معمول أصلاً إنه يسمح بالقراية ويوقف التعديلات لحد ما الخطة يتوافق عليها.
If the finished change will be a small diff, plan mode is unnecessary, even while several competing approaches remain undecided.
لو التغيير النهائي هيطلع تعديل صغير، يبقى مش محتاج وضع التخطيط، حتى لو لسه فيه كذا طريقة بيتنافسوا ومتحسمش أي واحدة فيهم.
What calls for plan mode is a decision that must precede edits, not diff size; when choosing between approaches is the hard part, that choice should be settled before anything is written.
اللي بيستدعي وضع التخطيط هو إن فيه قرار لازم ييجي قبل التعديلات، مش حجم التعديل؛ ولما الاختيار بين الطرق يبقى هو الجزء الصعب، الاختيار ده لازم يتحسم قبل ما أي حاجة تتكتب.
Use plan mode to decide, then implement the small change directly.
استخدم وضع التخطيط عشان تقرر، وبعدين نفّذ التغيير الصغير على طول.
Instead of planning, you can let a large restructuring run headless under bypassPermissions and review the PR it produces.
بدل التخطيط، ممكن تسيب إعادة هيكلة كبيرة تشتغل من غير واجهة تفاعلية تحت bypassPermissions وتراجع الـ PR اللي يطلع.
bypassPermissions is designed for use in isolated containers and VMs. Also, the design gets reviewed only once all the code is written, so a wrong direction costs a reverted diff rather than an edited plan.
bypassPermissions معمول للاستخدام في الحاويات والأجهزة الافتراضية المعزولة. وكمان التصميم مش هيتراجع غير بعد ما الكود كله يتكتب، فلو الاتجاه غلط هتدفع تمنه تعديلات تلغيها كلها بدل خطة تعدّلها.
Explore and propose in plan mode with edits held, then implement after approval.
استكشف واقترح في وضع التخطيط والتعديلات متوقفة، وبعدين نفّذ بعد الموافقة.
On a large change, plan mode only adds cost, since it reaches the same edits by a slower path.
في التغيير الكبير، وضع التخطيط بيزود التكلفة وبس، لأنه بيوصل لنفس التعديلات بس من طريق أبطأ.
Planning prevents rework: it fixes one consistent pattern before editing and catches flawed approaches when a correction costs one message instead of rewinding many changed files.
التخطيط بيمنع إعادة الشغل: بيثبّت طريقة واحدة متسقة قبل التعديل، وبيمسك الطرق الغلط في الوقت اللي التصحيح فيه بيكلف رسالة واحدة، بدل ما ترجّع ملفات كتير اتغيرت.
Treat plan mode as the cheaper path for large, multi-approach or architectural changes.
اعتبر وضع التخطيط هو الطريق الأرخص للتغييرات الكبيرة، أو اللي فيها أكتر من طريقة، أو اللي ليها تأثير على معمارية النظام.
Once a task begins in plan mode, it should remain there while the implementation is carried out.
أول ما المهمة تبدأ في وضع التخطيط، لازم تفضل فيه وإنت بتنفّذ.
Approving the plan is the review; staying in plan mode afterwards would hold back exactly the edits that the plan requires.
الموافقة على الخطة هي نفسها المراجعة؛ ولو فضلت في وضع التخطيط بعدها هيوقف بالظبط التعديلات اللي الخطة محتاجاها.
After approval, switch to an editing mode and execute directly against the plan.
بعد الموافقة، حوّل لوضع تعديل ونفّذ على طول على حسب الخطة.
When Claude reads file after file in plan mode with no prompts, either the mode quietly changed to acceptEdits or permission checks have been disabled.
لما Claude يقرا ملف ورا ملف في وضع التخطيط من غير ما يطلب أي إذن، يبقى يا إما الوضع اتغير لـ acceptEdits من غير ما تحس، يا إما فحوصات الصلاحيات اتقفلت.
Free reading with no edits is plan mode working as designed, and the mode never changes on its own.
القراية بحرية من غير تعديلات ده وضع التخطيط شغال زي ما هو معمول، والوضع عمره ما بيتغير لوحده.
Understand that plan mode permits reading and withholds edits until you approve.
افهم إن وضع التخطيط بيسمح بالقراية وبيمنع التعديلات لحد ما توافق.
How the exam tests this
  • Free reading with zero edits in plan mode is the intended behaviour. Answers that blame a quiet change to acceptEdits, or some setting that turned permission checks off, are distractors.

3.5 Apply iterative refinement techniques for progressive improvement

If Claude gets a transformation wrong from your prose description, the remedy is a longer, more detailed description.

هيبقى عندك تحقق مستقل لو Claude كتب الكود وكمان اختبارات الوحدة بتاعته، وطلّع المخرجات المتوقعة من البرومبت بتاعك.

الاختبارات دي بتعكس فهم Claude لنفس الوصف المبهم، فممكن تعدّي حتى لو السلوك غلط؛ وفي الآخر الوكيل اللي عمل الشغل هو اللي بيصحح شغله بنفسه.

حط المخرجات المتوقعة بنفسك، أو ضيف فحص مستقل فيه موديل جديد بيحاول يثبت إن النتيجة غلط.
A sensible way to deal with the edge case is to put the failing transformation inside a try/except that logs the bad records.
طريقة معقولة تتعامل بيها مع الحالة الطرفية إنك تحط التحويل اللي بيفشل جوه بلوك يلتقط الاستثناءات ويسجّل السجلات البايظة.
Logging and continuing suppresses the symptom without fixing the root cause, so the affected records still are not migrated.
إنك تسجّل الخطأ وتكمّل ده بيداري العَرَض من غير ما يصلح السبب الأساسي، فالسجلات المتأثرة برضه مش بتترحّل.
Fix the root cause, for example by giving Claude the exact expected output for that edge case.
صلّح السبب الأساسي، مثلاً إنك تدّي Claude المخرجات المتوقعة بالظبط للحالة الطرفية دي.
Iteration is always most efficient when you paste the complete test output, all failures included, into a single message.
التكرار دايماً بيبقى أكفأ لما تلزق مخرجات الاختبارات كلها، بكل حالات الفشل اللي فيها، في رسالة واحدة.
That suits only failures whose fixes interact; for independent failures it mixes unrelated changes that should be confirmed separately and hides which change broke a later run.
ده مناسب بس لحالات الفشل اللي إصلاحاتها مرتبطة ببعض؛ أما في حالات الفشل المستقلة فبيخلط تغييرات ملهاش علاقة ببعض المفروض كل واحد يتأكد منه لوحده، وبيخبّي أنهي تغيير هو اللي بوّظ تشغيل بعد كده.
Report independent failures one per message in sequence; report interacting failures together with how they relate.
ابعت حالات الفشل المستقلة كل واحدة في رسالة بالترتيب؛ وحالات الفشل المرتبطة ابعتها مع بعض ومعاها إزاي هي مرتبطة.
A mishandled edge case will be fixed if you start a new session and have Claude regenerate the entire script.
الحالة الطرفية اللي اتعالجت غلط هتتصلح لو بدأت جلسة جديدة وخليت Claude يكتب البرنامج كله من الأول.
Starting again from the same description that produced the bug makes the same misreading just as likely; a fresh start only helps with a better prompt.
لو بدأت تاني من نفس الوصف اللي طلّع المشكلة، احتمال نفس الفهم الغلط يتكرر هو هو؛ البداية الجديدة بتفيد بس لو معاها برومبت أحسن.
Add a concrete example or failing test that pins down the edge case.
ضيف مثال ملموس أو اختبار فاشل بيحدد الحالة الطرفية بالظبط.
Claude stays focused if you omit some of the failures when you report them.
Claude بيفضل مركّز لو شيلت شوية من حالات الفشل وإنت بتبلّغ عنها.
Sequential reporting still fixes every failure in turn rather than dropping any, and with interacting failures omitting one invites a misdirected fix.
التبليغ بالترتيب برضه بيصلح كل فشل في دوره من غير ما يسيب أي واحد، ولو حالات الفشل مرتبطة ببعض فإنك تشيل واحدة منهم بيفتح الباب لإصلاح في المكان الغلط.
Report all failures: one at a time if independent, together if they interact.
بلّغ عن كل حالات الفشل: واحدة واحدة لو مستقلة، ومع بعض لو مرتبطة.
How the exam tests this
  • Watch for an answer where Claude writes the converter and also its unit tests, taking the expected outputs from your prompt. It sounds thorough but is a distractor, because those tests inherit Claude's misreading; you have to supply the expected outputs, and grading should not be left to the agent that did the work.
