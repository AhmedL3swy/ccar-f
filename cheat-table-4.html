4.1

Precision & false positives

5

Reduce false positives and improve accuracy.

Do

  • Use explicit detection criteria.
  • Define clear rules (with a concrete example) for each severity level.
  • Add examples of acceptable patterns that should NOT be reported.
  • If a category has repeated false positives, disable it temporarily, refine it and test.

Avoid

  • Vague or general instructions ("be conservative").
  • Inconsistent severity definitions.
  • Relying on high confidence alone, without clear criteria and evidence.
4.2

Few-shot prompting

5

Use examples to guide Claude's behaviour.

How it helps

  • Provide representative input/output examples.
  • Include ambiguous cases and edge cases.
  • Show correct labels, especially for easily confused categories.

Example

Input

Password stored in plain text

{
  "category": "Security"
}

Remember

Examples teach Claude the pattern better than instructions alone.

4.3

Structured output

4

Consistent, machine-readable results.

JSON

The actual output format.

{
  "severity": "high",
  "file": "LoginViewModel.swift",
  "line": 42,
  "message": "Missing error handling"
}

JSON Schema

Defines required fields, types and constraints.

{
  "type": "object",
  "required": ["severity",
    "file", "line", "message"]
}

Validation levels

  1. Schema validationChecks structure, required fields and data types.
  2. Semantic validationChecks the finding is actually correct and matches the code and criteria.

Valid structure ≠ valid content

JSON can be schema-valid and still contain an incorrect finding.

4.4

Validation, retry & feedback

5

Handle invalid outputs reliably.

  1. ValidateCheck the output against the schema and rules.
  2. Provide specific feedbackSend Claude the exact validation errors.
  3. Retry with a limitAllow a limited number of correction attempts.
  4. Handle failureIf retries run out, fail gracefully and take an appropriate action.

Example error feedback

Validation errors:

  • severity must be one of: critical, high, medium, low
  • line must be an integer

Correct the output to satisfy the schema.

Works well for

  • Invalid JSON
  • Missing required fields
  • Schema violations

May not be enough for

  • Incorrect business logic
  • Issues that need deeper reasoning
4.5

Message Batches

6

Process many requests efficiently.

Use when

  • Large numbers of independent requests.
  • Results aren't needed immediately.
  • Reducing API cost is a priority (50% of standard price).

Avoid when

  • A response is needed immediately (a user is waiting).
  • The next step depends on the current result.
  • A tight deadline needs synchronous processing (batches only promise ≤ 24 h).

Example

Good fitClassify 5,000 support tickets overnight.
Not a good fitReview a PR while the developer waits for results.

Multi-instance & multi-pass review

5

Improve review quality and coverage.

Multi-instance (independent review)

Instance AGenerates code
→
Instance BReviews code (independent context)
  • Use a separate review instance to reduce bias from the generation session's context.

Multi-pass review

Break complex reviews into focused passes.

Pass 1Correctness (bugs, logic)
→
Pass 2Security (vulnerabilities)
→
Pass 3Performance (expensive ops)

Key takeaways

  1. Be explicit and provide clear criteria.
  2. Use examples to guide Claude's behaviour.
  3. Enforce structured outputs and validate them.
  4. Use actionable feedback with limited retries.
  5. Choose the right processing method (sync vs batches).
  6. Use independent instances and multi-pass reviews for higher quality.

Do vs don't

Do

  • Use clear, specific prompts.
  • Provide representative examples.
  • Define structured outputs with JSON Schema.
  • Validate and give specific feedback.
  • Batch high-volume, non-urgent tasks.
  • Use separate instances and multi-pass reviews.

Don't

  • Use vague instructions.
  • Rely on high confidence alone.
  • Assume schema validity means correctness.
  • Retry without feedback.
  • Use batches for time-critical requests.
  • Review in the same session that generated the code.

4.1

Design prompts with explicit criteria to improve precision and reduce false positivesإزاي تصمم برومبتات فيها معايير صريحة عشان تحسّن الدقة وتقلل الإنذارات الكاذبة

Key factsمعلومات مهمة 7

  • REVIEW.md File where teams tailor Anthropic's Code Review, setting which issues get flagged, how severe each one is, and how it gets reported.
    REVIEW.md الملف اللي الفرق بتظبط فيه Code Review بتاع Anthropic: أنهي مشاكل تتعلّم، وكل واحدة درجة خطورتها قد إيه، وبتتبلّغ إزاي.
  • ## Do not report / ## Always check Example REVIEW.md sections holding the skip list and the always-check list.
    ## Do not report / ## Always check أمثلة لأقسام في REVIEW.md فيها قائمة التجاهل وقائمة «افحص دايماً».
  • CLAUDE.md in Code Review Treated as project context; new violations of it are flagged as nits.
    CLAUDE.md في Code Review بيتعامل معاه كسياق للمشروع؛ وأي مخالفة جديدة ليه بتتعلّم كملاحظة بسيطة.
  • Code Review default scope Reports correctness bugs that would break production; formatting preferences and gaps in test coverage are excluded.
    النطاق الافتراضي لـ Code Review بيبلّغ عن الغلطات اللي بتخلي الكود يشتغل غلط وممكن تكسر بيئة الإنتاج؛ أما تفضيلات التنسيق والنواقص في تغطية الاختبارات فبرّه الحسبة.
  • Important / Nit / Pre-existing Code Review severity levels: fix before merging / minor and non-blocking / a defect that predates this PR.
    Important / Nit / Pre-existing مستويات الخطورة في Code Review: صلّحها قبل الدمج / حاجة بسيطة ومش بتوقف الدمج / غلطة موجودة من قبل الـ PR ده.
  • <security_criteria>, <correctness_criteria>, <style_criteria> Example descriptive tag names for isolating each category's rules and examples.
    <security_criteria>, <correctness_criteria>, <style_criteria> أمثلة لأسماء وسوم وصفية عشان تعزل قواعد وأمثلة كل فئة لوحدها.
  • Feedback count Code Review analytics metric counting comments auto-resolved after a developer fixed the flagged issue; a rough live signal that misses ignored or missed findings.
    مقياس «عدد الردود» مقياس في إحصائيات Code Review بيعدّ التعليقات اللي اتقفلت لوحدها بعد ما المطوّر صلّح المشكلة اللي اتعلّم عليها؛ إشارة لحظية تقريبية، بس مبتشوفش الملاحظات اللي اتجاهلت أو اللي فاتت.

  • Explicit categorical criteria Prompt rules that say which finding types get reported and which get skipped.
    معايير فئات صريحة (Explicit categorical criteria) قواعد في البرومبت بتقول أنهي أنواع ملاحظات تتبلّغ وأنهي تتساب.
  • False positive A reported finding that is not a real problem.
    إنذار كاذب (False positive) ملاحظة اتبلّغ عنها وهي مش مشكلة حقيقية.
  • Precision Of the findings reported, the fraction that are real.
    الدقة (Precision) من الملاحظات اللي اتبلّغت، نسبة الحقيقي فيها.
  • Recall The share of real issues in a known-answer set that the reviewer actually reports.
    نسبة الاكتشاف (Recall) نسبة المشاكل الحقيقية في مجموعة حالات إجابتها معروفة اللي المراجِع بلّغ عنها فعلاً.
  • F1 A single score balancing precision and recall.
    مقياس F1 رقم واحد بيوازن بين الدقة ونسبة الاكتشاف.
  • Skip list The never-report list of categories a reviewer must ignore, also usable to disable a noisy category temporarily.
    قائمة التجاهل (Skip list) قائمة «متبلّغش أبداً» للفئات اللي المراجِع لازم يتجاهلها، وينفع تستخدمها كمان عشان تقفل فئة دوشة مؤقتاً.
  • Severity anchor A concrete code example tied to a severity level so the label is applied consistently.
    مثال مرجعي لدرجة الخطورة (Severity anchor) مثال كود محدد مربوط بمستوى خطورة عشان التصنيف يتطبق بنفس الشكل كل مرة.
4.2

Apply few-shot prompting to improve output consistency and qualityاستخدم الأمثلة التوضيحية عشان تحسّن ثبات المخرجات وجودتها

Key factsمعلومات مهمة 4

  • <example> / <examples> Tags wrapping each example and the whole set so they are not mistaken for instructions.
    <example> / <examples> وسوم بتلف كل مثال والمجموعة كلها عشان ميتفهموش غلط على إنهم تعليمات.
  • 2-4 examples Recommended size of a targeted set aimed at ambiguous cases, each with its reasoning.
    2-4 أمثلة الحجم المنصوح بيه لمجموعة مركّزة على الحالات الملخبطة، كل مثال معاه التبرير بتاعه.
  • input_examples List of sample calls in a tool definition (tool use examples) showing usage the schema cannot convey.
    input_examples قائمة استدعاءات كأمثلة جوه تعريف الأداة (أمثلة استخدام الأداة) بتوضح استخدام المخطط ميقدرش يوصّله.
  • 72% to 90% Accuracy improvement on complex parameter handling that Anthropic reported from tool use examples teaching formats, ID patterns and optional-field combinations.
    من 72% لـ 90% التحسن في الدقة في التعامل مع المُعاملات المعقدة اللي Anthropic أعلنته من أمثلة استخدام الأداة اللي بتعلّم الأشكال وأنماط الـ ID وتركيبات الحقول الاختيارية.

Termsمصطلحات 6

  • Few-shot prompting Steering output with a small set of worked input-output examples in the prompt.
    أمثلة توضيحية (Few-shot prompting) توجيه المخرجات بمجموعة صغيرة من أمثلة محلولة (مدخل ومخرج) جوه البرومبت.
  • Canonical examples A few representative, diverse examples chosen to convey the rule rather than enumerate cases.
    أمثلة نموذجية (Canonical examples) شوية أمثلة ممثّلة ومتنوعة، متختارة عشان توصّل القاعدة مش عشان تعدّ الحالات.
  • Laundry list An exhaustive list of edge-case pairs, which the model pattern-matches against rather than generalizing from.
    قائمة كل الحالات (Laundry list) قائمة شاملة لأزواج كل الحالات الحدّية، الموديل بيطابق عليها بالشكل بدل ما يعمم منها.
  • Contrast pair Two look-alike examples that differ only on the deciding factor, one acceptable and one an issue.
    مثالين متقابلين (Contrast pair) مثالين شبه بعض بيختلفوا بس في العامل الحاسم، واحد مقبول والتاني مشكلة.
  • Tool use examples Sample tool calls (input_examples) placed in a tool definition to show correct usage.
    أمثلة استخدام الأداة (Tool use examples) استدعاءات أداة كأمثلة (input_examples) بتتحط في تعريف الأداة عشان توضح الاستخدام الصح.
  • Unintended pattern An accidental trait shared by all examples, such as length or language, that the model wrongly treats as signal.
    نمط غير مقصود (Unintended pattern) صفة مشتركة بين كل الأمثلة بالصدفة، زي الطول أو اللغة، والموديل بيتعامل معاها غلط على إنها إشارة.
4.3

Enforce structured output using tool use and JSON schemasإزاي تفرض مخرجات منظّمة باستخدام الأدوات ومخططات JSON

Key factsمعلومات مهمة 10

  • input_schema The tool definition key holding the JSON Schema that, for extraction, is the output record shape.
    input_schema المفتاح في تعريف الأداة اللي فيه مخطط JSON، واللي في استخراج البيانات بيبقى هو شكل سجل المخرجات.
  • stop_reason: tool_use Signals Claude called a tool; the result lives in the tool_use block's input.
    stop_reason: tool_use معناه إن Claude استدعى أداة؛ والنتيجة موجودة في الـ input بتاع جزء tool_use.
  • strict: true Compiles the schema into a grammar so tool inputs always match it and the tool name is valid.
    strict: true بيحوّل المخطط لقواعد صياغة فمدخلات الأداة دايماً مطابقة ليه واسم الأداة سليم.
  • additionalProperties: false Set on strict schemas so Claude cannot add undeclared keys.
    additionalProperties: false بيتحط في المخططات الصارمة عشان Claude ميقدرش يزوّد مفاتيح مش متعرّفة.
  • output_config.format JSON outputs feature returning schema-valid JSON in a text block without any tool call.
    output_config.format خاصية مخرجات JSON اللي بترجّع JSON مطابق للمخطط جوه جزء نصّي من غير أي استدعاء أداة.
  • {"type": "auto"} Claude decides whether and which tool to call; text before a tool call is allowed; no guarantee.
    {"type": "auto"} Claude بيقرر هيستدعي أداة ولا لأ وأنهي واحدة؛ مسموح بنص قبل استدعاء الأداة؛ مفيش ضمان.
  • {"type": "any"} Some provided tool must be called, Claude picks which; no text before the tool_use block.
    {"type": "any"} لازم أداة من الأدوات المتاحة تتستدعى، وClaude بيختار أنهي واحدة؛ مفيش نص قبل جزء tool_use.
  • {"type": "tool", "name": ...} The named tool must be called; no text or thinking before the tool_use block.
    {"type": "tool", "name": ...} الأداة اللي اسمها متحدد لازم تتستدعى؛ مفيش نص ولا تفكير قبل جزء tool_use.
  • {"type": "none"} Tools are disabled for the turn; text only.
    {"type": "none"} الأدوات مقفولة في الدور ده؛ نص بس.
  • 400 error on newest models Sonnet 5.5, Opus 5.5, Mythos 5.1 and Fable 5.1 reject any and forced tool; instead use auto + strict + tool named in prompt.
    خطأ 400 على أحدث الموديلات Sonnet 5.5 وOpus 5.5 وMythos 5.1 وFable 5.1 بيرفضوا any وtool المفروضة؛ استخدم بدلهم auto + الوضع الصارم + اسم الأداة في البرومبت.

  • Extraction tool A never-executed tool whose input schema defines the structured record Claude returns.
    أداة استخراج (Extraction tool) أداة عمرها ما بتتنفذ، ومخطط المدخلات بتاعها بيحدد السجل المنظّم اللي Claude بيرجّعه.
  • Strict tool use Constrained decoding that guarantees tool inputs conform to the declared schema.
    الوضع الصارم لاستخدام الأدوات (Strict tool use) توليد مقيّد بيضمن إن مدخلات الأداة مطابقة للمخطط المعلن.
  • Syntax error A structural defect such as malformed JSON, a wrong type, a missing required key or an undeclared property.
    خطأ في البنية (Syntax error) عيب في البنية زي JSON بايظ، أو نوع بيانات غلط، أو مفتاح مطلوب ناقص، أو خاصية مش متعرّفة.
  • Semantic error Output that is structurally valid but wrong about the source document.
    خطأ في المعنى (Semantic error) مخرجات بنيتها سليمة بس كلامها غلط عن المستند الأصلي.
  • Escape value An enum option like other or unclear that gives the model a correct choice when no listed category fits.
    قيمة مَخرج (Escape value) اختيار في قائمة القيم زي other أو unclear بيدّي الموديل اختيار صح لما مفيش فئة في القائمة مناسبة.
  • Nullable field A field that may hold null so 'not in the document' is an explicit, visible answer.
    حقل يقبل القيمة الفاضية (Nullable field) حقل ممكن ياخد القيمة الفاضية عشان 'مش موجود في المستند' تبقى إجابة صريحة وباينة.
  • JSON outputs Schema-constrained JSON returned in a text block via output_config.format, with no tool involved.
    مخرجات JSON (JSON outputs) JSON مقيّد بالمخطط بيرجع جوه جزء نصّي عن طريق output_config.format، من غير أي أداة.
4.4

Implement validation, retry, and feedback loops for extraction qualityإزاي تبني التحقق وإعادة المحاولة وحلقات التغذية الراجعة عشان جودة استخراج البيانات

Key factsمعلومات مهمة 7

  • stated_total Self-correction field holding the total as printed on the document.
    stated_total حقل تصحيح ذاتي فيه الإجمالي زي ما هو مطبوع في المستند.
  • calculated_total Self-correction field holding the model's own sum of the extracted line items, compared against stated_total by your validator.
    calculated_total حقل تصحيح ذاتي فيه مجموع بنود الفاتورة اللي الموديل طلّعها بحسابه هو، وأداة التحقق بتاعتك بتقارنه بـ stated_total.
  • conflict_detected Boolean the model sets when the source document itself contains contradictory values.
    conflict_detected قيمة منطقية (آه أو لأ) الموديل بيفعّلها لما المستند الأصلي نفسه يبقى فيه قيم متناقضة.
  • is_error: true Key on a tool_result that tells Claude the call failed, so Claude reads the error and fixes its next attempt.
    is_error: true مفتاح في tool_result بيقول لـ Claude إن الاستدعاء فشل، فـ Claude يقرا الخطأ ويصلّح المحاولة الجاية.
  • error_max_structured_output_retries Agent SDK result subtype returned when structured-output retries are exhausted; your code must handle it.
    error_max_structured_output_retries نوع فرعي للنتيجة في الـ Agent SDK بيرجع لما محاولات المخرجات المنظّمة تخلص؛ والكود بتاعك لازم يتعامل معاه.
  • detected_pattern Finding field naming the code construct that triggered it, enabling dismissal rates per construct.
    detected_pattern حقل في الملاحظة بيسمّي تركيبة الكود اللي طلّعتها، فتقدر تحسب نسبة الرفض لكل تركيبة.
  • minimum in SDK helpers Example of a constraint SDK helpers remove from the schema Claude receives and verify in code afterwards.
    minimum في الدوال المساعدة في الـ SDK مثال لقيد الدوال المساعدة في الـ SDK بتشيله من المخطط اللي Claude بيستلمه وبتتحقق منه في الكود بعدين.

Termsمصطلحات 7

  • Semantic error A schema-valid value that is wrong relative to the source or to other fields.
    خطأ في المعنى (Semantic error) قيمة سليمة حسب المخطط بس غلط بالنسبة للمصدر أو للحقول التانية.
  • Validation layer Your post-extraction code that enforces every rule the schema cannot express.
    طبقة التحقق (Validation layer) الكود بتاعك اللي بعد استخراج البيانات واللي بيفرض كل قاعدة المخطط ميقدرش يعبّر عنها.
  • Self-correction fields Extra output fields like stated_total and calculated_total that expose discrepancies for code to check.
    حقول التصحيح الذاتي (Self-correction fields) حقول زيادة في المخرجات زي stated_total وcalculated_total بتكشف الاختلافات عشان الكود يفحصها.
  • Retry with error feedback A follow-up request carrying the document, the failed output and specific errors so the model can fix them.
    إعادة المحاولة مع إرجاع الأخطاء (Retry with error feedback) طلب متابعة فيه المستند والمخرجات اللي فشلت والأخطاء المحددة عشان الموديل يصلّحها.
  • Escalation Stopping automated retries and routing the record to a person who can obtain the missing information.

4.1 Design prompts with explicit criteria to improve precision and reduce false positives

The trapWhy it's wrongWhat's actually trueTranslate
A noisy review prompt produces fewer false positives once you tell it to 'be conservative' or to 'only report high-confidence findings'.
برومبت المراجعة الدوشة هيطلّع إنذارات كاذبة أقل أول ما تقوله 'خليك متحفّظ' أو 'بلّغ بس عن الملاحظات اللي إنت واثق منها جداً'.
The model already labelled the false positives with confidence, so the same judgment lets them through; the wording only makes it hide real lower-ranked findings, lowering recall.
الموديل أصلاً حط الإنذارات الكاذبة دي وهو واثق منها، فنفس الحكم ده هيعدّيها؛ والصياغة دي كل اللي بتعمله إنها بتخليه يخبّي ملاحظات حقيقية ترتيبها أقل، فنسبة الاكتشاف تقل.
Replace confidence language with explicit categorical criteria stating what to report and what to skip.
شيل كلام الثقة وحط مكانه معايير فئات صريحة بتقول إيه اللي يتبلّغ وإيه اللي يتساب.
Any code that departs from the dominant style of the file around it is something the reviewer should flag.
أي كود بيخرج عن الأسلوب الغالب في الملف اللي حواليه لازم المراجِع يعلّم عليه.
Surrounding legacy code may follow outdated styles, so measuring against it flags the one function that correctly follows the project convention.
الكود القديم اللي حواليه ممكن يكون ماشي على أساليب عفا عليها الزمن، فلو قست عليه هتعلّم على الدالة الوحيدة اللي ماشية صح على قواعد المشروع المتفق عليها.
Judge style and naming against the documented project standard (e.g. CLAUDE.md), flagging only new violations of it.
احكم على الأسلوب والتسمية بالمعيار المكتوب بتاع المشروع (زي CLAUDE.md)، وعلّم بس على المخالفات الجديدة ليه.
Categories stay adequately separated if each gets a prose paragraph opening with its name, or if all examples sit in a single shared block at the end.
الفئات بتفضل منفصلة كويس لو كل واحدة ليها فقرة نثرية بتبدأ باسمها، أو لو كل الأمثلة متجمعة في قسم واحد مشترك في الآخر.
Prose depends on the model noticing where a category ends, and a shared examples block separates each example from the rules it illustrates, so thresholds leak between categories.
النثر بيعتمد إن الموديل ياخد باله الفئة بتخلص فين، وقسم الأمثلة المشترك بيفصل كل مثال عن القواعد اللي بيوضحها، فالحدود بتسرّب من فئة للتانية.
Wrap the rules and examples for each category together in a separate XML tag whose name describes that category.
لف قواعد وأمثلة كل فئة مع بعض في وسم XML منفصل اسمه بيوصف الفئة دي.
Adjectives such as 'serious' or 'important' are all a severity level needs to be well defined.
صفات زي 'خطير' أو 'مهم' كفاية عشان مستوى الخطورة يبقى متعرّف كويس.
An adjective sets no boundary: one run may call a defect critical and the next run call the same defect medium, and teams disagree about what 'high' means.
الصفة مبتحطش أي حد فاصل: مرة تشغيل ممكن تقول على غلطة إنها حرِجة والمرة اللي بعدها تقول على نفس الغلطة إنها متوسطة، والفرق بتختلف على معنى 'عالي'.
Define each level by concrete consequences and anchor each with a specific code example.
عرّف كل مستوى بعواقب ملموسة، وثبّت كل واحد بمثال كود محدد.
Switching off a noisy category shows it did not matter, or can replace fixing its prompt; re-enable it as soon as it generates fewer comments.
إنك تقفل فئة دوشة معناه إنها مكانتش مهمة، أو إن ده ممكن يغنيك عن تصليح البرومبت بتاعها؛ ورجّعها أول ما تطلّع تعليقات أقل.
Disabling is a temporary trust-protection step while criteria are rewritten, and 'fewer comments' can mean real findings were dropped.
القفل ده خطوة مؤقتة عشان تحمي الثقة لحد ما المعايير تتكتب من جديد، و'تعليقات أقل' ممكن يكون معناها إن ملاحظات حقيقية وقعت.
Rewrite the criteria explicitly, test against known-answer cases using recall or F1, then re-enable.
اكتب المعايير من جديد بشكل صريح، واختبرها على حالات إجابتها معروفة بنسبة الاكتشاف أو F1، وبعدين رجّعها.
How the exam tests this
  • Options that try to quiet a noisy reviewer with confidence or caution language are distractors. The correct choice replaces that language with a concrete rule saying what gets reported and what gets skipped.
  • Turning a noisy category off is a deliberate, short-term move that preserves trust in the remaining categories while that category's criteria get rewritten. It neither means the category is unimportant nor replaces fixing its prompt.

الوضع الصارم بيفحص البنية بس؛ قيمة من القائمة سليمة بس غلط، أو قيمة في حقل غلط، أو بنود فاتورة مجموعها مش بيساوي الإجمالي، كل دول بيعدّوا.
Add semantic checks in your own code after extraction and feed failures back to Claude.
زوّد فحوصات للمعنى في الكود بتاعك بعد استخراج البيانات، ورجّع أي أخطاء لـ Claude عشان يصلّحها.
How the exam tests this
  • For the exam, forcing tool_choice is how you guarantee one specific extraction. Know, though, that any and tool produce a 400 error on Claude Sonnet 5.5, Opus 5.5, Mythos 5.1 and Fable 5.1, where the documented workaround is to use auto, turn on strict tool use, and name the tool in the prompt.

4.4 Implement validation, retry, and feedback loops for extraction quality

The trapWhy it's wrongWhat's actually trueTranslate
Strict tool use ensures the output complies with the schema, which means the extracted values are right and no more validation is needed.
الوضع الصارم لاستخدام الأدوات بيضمن إن المخرجات مطابقة للمخطط، يعني القيم اللي اتطلّعت صح ومش محتاج تحقق تاني.
Strict mode guarantees types and required keys only; misplaced values and cross-field disagreements are individually valid and pass.
الوضع الصارم بيضمن أنواع البيانات والمفاتيح المطلوبة بس؛ القيم اللي في مكان غلط والتناقض بين الحقول كل واحدة فيهم سليمة لوحدها فبتعدّي.
Run semantic checks in your own code (e.g. recompute sums, check object placement) after extraction.
شغّل فحوصات للمعنى في الكود بتاعك بعد استخراج البيانات (زي إنك تعيد حساب المجاميع، وتتأكد إن كل قيمة في الكائن الصح).
If individually valid fields contradict each other, the fix is a tighter schema, extra worked examples, or a retry at temperature 0 that takes the first valid response.
لو حقول كل واحد فيها سليم لوحده بيناقضوا بعض، الحل مخطط أضيق، أو أمثلة محلولة زيادة، أو إعادة محاولة بدرجة حرارة 0 تاخد أول رد سليم.
Each value is valid on its own, so none of these detects the mismatch; it is wrong only relative to the other fields.
كل قيمة سليمة لوحدها، فولا حاجة من دول هتكتشف عدم التطابق؛ هي غلط بس بالنسبة للحقول التانية.
After extraction, run a semantic check, for example adding up the line items again and checking the result against the stated total.
بعد استخراج البيانات شغّل فحص للمعنى، مثلاً اجمع بنود الفاتورة تاني وقارن النتيجة بالإجمالي المكتوب.
Since the model remembers what it extracted, a retry message can consist of just the validation errors.
بما إن الموديل فاكر هو طلّع إيه، رسالة إعادة المحاولة ممكن يبقى فيها أخطاء التحقق بس.
A retry is often a new request with nothing carried over; without the document the model just rearranges its old JSON, and without the failed output it cannot keep the correct parts.
إعادة المحاولة غالباً طلب جديد مفيش فيه أي حاجة متنقلة من اللي قبله؛ من غير المستند الموديل هيعيد ترتيب الـ JSON القديم بتاعه وخلاص، ومن غير المخرجات اللي فشلت مش هيقدر يحافظ على الأجزاء الصح.
Include all three in one request: the specific validation errors, the failed extraction and the original document.
حط التلاتة في طلب واحد: أخطاء التحقق المحددة، والاستخراج اللي فشل، والمستند الأصلي.
A required field that stays empty through several retries will get filled sooner or later by tightening the schema, rescanning at higher sharpness or switching to a bigger model.
الحقل المطلوب اللي فاضل فاضي بعد كذا إعادة محاولة هيتملي عاجلاً أو آجلاً لو ضيّقت المخطط، أو عملت مسح ضوئي تاني بوضوح أعلى، أو غيّرت لموديل أكبر.
If none of the model's inputs contain the value, these measures can only shape or reread something that does not exist, and they nudge the model into fabricating it.
لو ولا مدخل من اللي الموديل خدهم فيه القيمة، الحاجات دي كل اللي تقدر تعمله إنها تشكّل أو تعيد قراية حاجة مش موجودة، وبتزق الموديل إنه يألّفها.
Stop retrying, make the field optional or nullable, and escalate to a person or supply the missing document.
بطّل إعادة المحاولة، وخلي الحقل اختياري أو يقبل القيمة الفاضية، وصعّد لشخص أو هات المستند الناقص.
To work out which findings developers reject as false positives, adding a dismissal_reason field or a confidence field is sufficient.
عشان تعرف أنهي ملاحظات المطورين بيرفضوها كإنذارات كاذبة، كفاية تزوّد حقل زي dismissal_reason أو حقل للثقة.
A dismissal reason says why findings were rejected but not which code triggered them, and confidence describes the model's certainty, not the construct.
سبب الرفض بيقول الملاحظات اترفضت ليه بس مش بيقول أنهي كود طلّعها، والثقة بتوصف قد إيه الموديل متأكد، مش تركيبة الكود.
Add a detected_pattern field naming the code construct and log it with each dismissal.
زوّد حقل اسمه detected_pattern بيسمّي تركيبة الكود، وسجّله مع كل رفض.
How the exam tests this
  • When each field passes on its own yet the values contradict one another, pick the option that adds a semantic check in your own code, for instance recalculating a sum and checking it against the stated total. A tighter schema, more prompt examples or a temperature-0 retry are distractors, since none of them catches the mismatch.
  • Start by asking where the failure originates. A value that is present in the supplied document but has the wrong form or sits in the wrong place calls for a retry with feedback. A value absent from everything the model was given means the answer is to stop and escalate; options that keep retrying, move to a larger model or enhance the image are wrong.

4.5 Design efficient batch processing strategies

The trapWhy it's wrongWhat's actually trueTranslate
Any human-readable label works as a custom_id, even one containing hashes, colons, slashes or spaces.
أي اسم مقروء ينفع يبقى custom_id، حتى لو فيه علامات # أو نقطتين (:) أو شُرَط مايلة (/) أو مسافات.
custom_id must match ^[a-zA-Z0-9_-]{1,64}$, so dots, hashes, colons, slashes and spaces are all rejected by validation.
custom_id لازم يطابق ^[a-zA-Z0-9_-]{1,64}$، فالنقط وعلامات # والنقطتين والشُرَط المايلة والمسافات كلها التحقق بيرفضها.
Use only letters, digits, hyphens and underscores, unique within the batch, e.g. doc-2026-report_final.
استخدم حروف وأرقام وشُرَط وشُرَط سفلية بس، ومن غير تكرار جوه الدفعة، زي doc-2026-report_final.
Since most batches complete in under an hour, polling a batch until it finishes works well for a blocking check such as a pre-merge gate.
بما إن أغلب الدفعات بتخلص في أقل من ساعة، إنك تفضل تسأل على حالة دفعة لحد ما تخلص بينفع كويس لفحص لازم يخلص قبل ما الشغل يكمّل، زي بوابة الفحص قبل الدمج.
The only guarantee is completion or expiry within 24 hours, so a blocked developer's wait has no practical upper bound; you cannot plan around the typical case.
الضمان الوحيد إنها تخلص أو مهلتها تنتهي خلال 24 ساعة، فانتظار المطوّر اللي واقف مالوش حد أقصى عملي؛ ومينفعش تخطط على الحالة المعتادة.
Use the synchronous Messages API and read the verdict directly from the response.
استخدم الـ Messages API المتزامن واقرا الحكم من الرد على طول.
Your application's tool-calling loop can run inside a batch request, with tools executed between turns until it finishes.
حلقة استدعاء الأدوات بتاعة تطبيقك ممكن تشتغل جوه طلب دفعة، والأدوات تتنفذ بين الأدوار لحد ما تخلص.
A batch request is single-shot with no client present mid-request to execute your tool and return a tool_result; only server-side tools run inside it.
طلب الدفعة بيتبعت مرة واحدة ومفيش تطبيق عندك موجود في نص الطلب يشغّل الأداة بتاعتك ويرجّع tool_result؛ أدوات السيرفر بس هي اللي بتشتغل جواه.
Keep the client tool loop on the synchronous API and batch only single-pass steps such as triage.
خلي حلقة الأدوات بتاعة تطبيقك على الـ API المتزامن، وحط في الدفعة الخطوات اللي بتخلص في جولة واحدة بس زي الفرز.
Because results are returned in the order requests were submitted, line n of the output matches request n.
عشان النتايج بترجع بنفس ترتيب الطلبات اللي اتبعتت، السطر رقم ن في المخرجات بيقابل الطلب رقم ن.
The .jsonl result lines are not guaranteed to follow request order.
سطور النتايج في ملف .jsonl مش مضمون إنها ماشية بترتيب الطلبات.
Match each result to its request by custom_id.
اربط كل نتيجة بالطلب بتاعها عن طريق custom_id.
If some requests fail, either rerun the entire batch or modify the failed requests inside the batch already submitted.
لو شوية طلبات فشلت، يا إما تعيد تشغيل الدفعة كلها، يا إما تعدّل الطلبات اللي فشلت جوه الدفعة اللي اتبعتت.
Rerunning everything pays again for results you already have, and a submitted batch cannot be modified.
إعادة تشغيل كل حاجة بتخليك تدفع تاني تمن نتايج عندك أصلاً، والدفعة اللي اتبعتت مينفعش تتعدّل.
Submit a new batch containing only the failed custom_ids, each with a fix for its specific error.
ابعت دفعة جديدة فيها قيم custom_id اللي فشلت بس، كل واحد معاه تصليح للخطأ بتاعه بالظبط.
Batch usage counts against your Messages API rate limits, and batches are limited to 1,000 or 500 requests per hour.
استخدام الدفعات بيتحسب من حدود معدل الـ Messages API بتاعتك، والدفعات محدودة بـ 1,000 أو 500 طلب في الساعة.
There is no hourly cap. A single batch may hold up to 100,000 requests and 256 MB, and separate limits govern batch usage.
مفيش حد بالساعة. الدفعة الواحدة ممكن تشيل لحد 100,000 طلب و256 MB، واستخدام الدفعات ليه حدود منفصلة.
Size batches against 100,000 requests / 256 MB; batch usage does not use Messages API rate limits.
حدد حجم الدفعات على أساس 100,000 طلب / 256 MB؛ واستخدام الدفعات مش بياكل من حدود معدل الـ Messages API.
How the exam tests this
  • Any option saying batches allow only 1,000 or 500 requests an hour is wrong. Each batch can contain up to 100,000 requests and 256 MB, HTTP calls and queued requests have their own rate limits, and batch usage never draws down Messages API rate limits.

4.6 Design multi-instance and multi-pass review architectures

The trapWhy it's wrongWhat's actually trueTranslate
An independent review is no different from raising extended thinking or asking the session that generated the code to critically re-examine its own design decisions.
المراجعة المستقلة مش مختلفة عن إنك تعلّي التفكير الموسّع أو تطلب من الجلسة اللي كتبت الكود إنها تراجع قرارات التصميم بتاعتها بعين ناقدة.
Because the reflection happens in the very context that produced the code, it falls back on the same justifications it is meant to be checking.
عشان المراجعة بتحصل في نفس السياق اللي طلّع الكود، فبترجع لنفس المبررات اللي المفروض هي بتفحصها.
Send the code to a separate instance with a fresh context (same model is fine) given only the code and requirements.
ابعت الكود لنسخة منفصلة بسياق جديد (نفس الموديل مفيش مشكلة)، وادّيها الكود والمتطلبات بس.
Since it is a subagent, picking the code-generating subagent's session back up and having it review its own diff qualifies as an independent review.
بما إنه وكيل فرعي، إنك ترجع تكمّل جلسة الوكيل الفرعي اللي كتب الكود وتخليه يراجع التعديلات بتاعته يتحسب مراجعة مستقلة.
A resumed session carries all of its prior context, so it keeps the generator's reasoning and anchors on old conclusions.
الجلسة اللي بتكمّلها بتبقى شايلة كل السياق اللي قبل كده، فبتحتفظ بتفكير الكاتب وبتتمسك باستنتاجات قديمة.
Start a fresh review subagent or second session that receives only the diff and the plan.
ابدأ وكيل فرعي جديد للمراجعة أو جلسة تانية تستلم التعديلات والخطة بس.
A disagreement between two per-file passes is best settled by the original generator, since it knows the reasons behind how the code was written.
أحسن حد يحسم الخلاف بين جولتين لملفين مختلفين هو الكاتب الأصلي، عشان هو عارف الأسباب ورا طريقة كتابة الكود.
That returns the review to the author, bias included; the passes conflict because each one saw only half of a bug that spans files.
كده بترجّع المراجعة للي كتب الكود، بالتحيّز بتاعه؛ والجولات متعارضة عشان كل واحدة فيهم شافت نص الغلطة بس، والغلطة دي ممتدة على أكتر من ملف.
Add a cross-file integration pass that reads the two files side by side and proposes a single fix based on the actual data flow.
زوّد جولة تكامل على أكتر من ملف تقرا الملفين جنب بعض وتقترح تصليح واحد مبني على مسار البيانات الحقيقي.
A multi-pass review gets better if the finding pass is told to 'only report high-severity issues' or to 'be conservative', because noise is removed early.
المراجعة على كذا جولة بتبقى أحسن لو قلت لجولة الاكتشاف 'بلّغ بس عن المشاكل اللي خطورتها عالية' أو 'خليك متحفّظ'، عشان الدوشة بتتشال بدري.
The finding pass then silently drops real issues below the bar, lowering recall, and the later verification pass never sees them.
ساعتها جولة الاكتشاف بترمي مشاكل حقيقية تحت الحد من غير ما تقول، فنسبة الاكتشاف تقل، وجولة التحقق اللي بعدها عمرها ما هتشوفها.
Have the finding pass report every issue with confidence and severity, and let a separate verification pass filter.
خلي جولة الاكتشاف تبلّغ عن كل مشكلة ومعاها درجة الثقة ودرجة الخطورة، وسيب التصفية لجولة تحقق منفصلة.
Code Review in Claude Code works as a quick merge gate, approving or blocking each pull request.
Code Review في Claude Code بيشتغل كبوابة دمج سريعة، بيوافق على كل PR أو بيوقفه.
Code Review posts comments only, never approving or blocking, and averages about 20 minutes per review.
Code Review بيكتب تعليقات بس، عمره ما بيوافق أو بيوقف، والمراجعة الواحدة بتاخد في المتوسط حوالي 20 دقيقة.
Choose Code Review when independently verified findings are wanted and the team accepts the wait and usage-credit cost.
اختار Code Review لما تكون عايز ملاحظات اتأكد منها بشكل مستقل والفريق موافق على الانتظار وتكلفة رصيد الاستخدام.
How the exam tests this
  • Choose Claude Code's Code Review when the scenario requires findings to be independently checked before anyone reads them and the team is fine with the cost and the wait. It runs agents in parallel, verifies findings, deduplicates them and ranks them by severity, takes roughly 20 minutes on average and bills through usage credits; it comments on the PR but never approves or blocks it.
