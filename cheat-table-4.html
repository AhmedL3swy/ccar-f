4.1

Precision & false positives

7

Reduce false positives and improve accuracy.

Do

  • Use explicit detection criteria.
  • Define clear rules (with a concrete example) for each severity level.
  • Add examples of acceptable patterns that should NOT be reported.
  • If a category has repeated false positives, disable it temporarily, refine it and test.

Avoid

  • Vague or general instructions ("be conservative").
  • Inconsistent severity definitions.
  • Relying on high confidence alone, without clear criteria and evidence.
4.2

Few-shot prompting

6

Use examples to guide Claude's behaviour.

How it helps

  • Provide representative input/output examples.
  • Include ambiguous cases and edge cases.
  • Show correct labels, especially for easily confused categories.

Example

Input

Password stored in plain text

{
  "category": "Security"
}

Remember

Examples teach Claude the pattern better than instructions alone.

4.3

Structured output

6

Consistent, machine-readable results.

JSON

The actual output format.

{
  "severity": "high",
  "file": "LoginViewModel.swift",
  "line": 42,
  "message": "Missing error handling"
}

JSON Schema

Defines required fields, types and constraints.

{
  "type": "object",
  "required": ["severity",
    "file", "line", "message"]
}

Validation levels

  1. Schema validationChecks structure, required fields and data types.
  2. Semantic validationChecks the finding is actually correct and matches the code and criteria.

Valid structure ≠ valid content

JSON can be schema-valid and still contain an incorrect finding.

4.4

Validation, retry & feedback

5

Handle invalid outputs reliably.

  1. ValidateCheck the output against the schema and rules.
  2. Provide specific feedbackSend Claude the exact validation errors.
  3. Retry with a limitAllow a limited number of correction attempts.
  4. Handle failureIf retries run out, fail gracefully and take an appropriate action.

Example error feedback

Validation errors:

  • severity must be one of: critical, high, medium, low
  • line must be an integer

Correct the output to satisfy the schema.

Works well for

  • Invalid JSON
  • Missing required fields
  • Schema violations

May not be enough for

  • Incorrect business logic
  • Issues that need deeper reasoning
4.5

Message Batches

7

Process many requests efficiently.

Use when

  • Large numbers of independent requests.
  • Results aren't needed immediately.
  • Reducing API cost is a priority (50% of standard price).

Avoid when

  • A response is needed immediately (a user is waiting).
  • The next step depends on the current result.
  • A tight deadline needs synchronous processing (batches only promise ≤ 24 h).

Example

Good fitClassify 5,000 support tickets overnight.
Not a good fitReview a PR while the developer waits for results.
4.6

Multi-instance & multi-pass review

6

Improve review quality and coverage.

Multi-instance (independent review)

Instance AGenerates code
→
Instance BReviews code (independent context)
  • Use a separate review instance to reduce bias from the generation session's context.

Multi-pass review

Break complex reviews into focused passes.

Pass 1Correctness (bugs, logic)
→
Pass 2Security (vulnerabilities)
→
Pass 3Performance (expensive ops)

Key takeaways

  1. Be explicit and provide clear criteria.
  2. Use examples to guide Claude's behaviour.
  3. Enforce structured outputs and validate them.
  4. Use actionable feedback with limited retries.
  5. Choose the right processing method (sync vs batches).
  6. Use independent instances and multi-pass reviews for higher quality.

Do vs don't

Do

  • Use clear, specific prompts.
  • Provide representative examples.
  • Define structured outputs with JSON Schema.
  • Validate and give specific feedback.
  • Batch high-volume, non-urgent tasks.
  • Use separate instances and multi-pass reviews.

Don't

  • Use vague instructions.
  • Rely on high confidence alone.
  • Assume schema validity means correctness.
  • Retry without feedback.
  • Use batches for time-critical requests.
  • Review in the same session that generated the code.

  • 72% to 90% Accuracy improvement on complex parameter handling that Anthropic reported from tool use examples teaching formats, ID patterns and optional-field combinations.
    من 72% لـ 90% التحسن في الدقة في التعامل مع المُعاملات المعقدة اللي Anthropic أعلنته من أمثلة استخدام الأداة اللي بتعلّم الأشكال وأنماط الـ ID وتركيبات الحقول الاختيارية.

  • Few-shot prompting Steering output with a small set of worked input-output examples in the prompt.

    400 invalid_request_error (رسالة «البرومبت طويل جداً») المدخل أكبر من نافذة السياق وهيفشل كل مرة لو متقسمش؛ والـ API بتاع عدّ التوكنز يقدر يمسكه قبلها.
  • stop_reason: "pause_turn" A server-tool turn in a batch result did not finish; continuing requires a new request.
    stop_reason: "pause_turn" دور فيه أداة سيرفر في نتيجة الدفعة مخلصش؛ وعشان تكمّل محتاج طلب جديد.

  • Dry run Sending the request shape through the synchronous API first to catch validation errors before batching.
    تجربة على الناشف (Dry run) إنك تبعت شكل الطلب على الـ API المتزامن الأول عشان تمسك أخطاء التحقق قبل ما تبعته في دفعة.

حدود فئة بتسرّب للفئة التانية
Wrap each category's rules and examples together in its own descriptively named XML tag, such as <security_criteria>لف قواعد وأمثلة كل فئة مع بعض في وسم XML خاص بيها اسمه بيوصفها، زي <security_criteria>
4.2 Apply few-shot prompting to improve output consistency and quality
The output format varies between runs
شكل المخرجات بيتغيّر من مرة للتانية
Few-shot examples showing the exact format; not temperature 0, a longer checklist or a reformatting callأمثلة few-shot بالشكل المطلوب بالظبط؛ مش temperature 0 ولا قائمة بنود أطول ولا استدعاء تاني يعيد التنسيق
Criteria are clear, but ambiguous cases go wrong
المعايير واضحة بس الحالات الملخبطة بتطلع غلط
2 to 4 few-shot examples that show the reasoning2 لـ 4 أمثلة few-shot بتوضّح طريقة التفكير
Extraction fails on documents with different layouts
الاستخراج بيفشل مع مستندات تنسيقها مختلف
Few-shot examples covering those layoutsأمثلة few-shot بتغطي التنسيقات دي
Extraction invents values and every few-shot example is fully filled
الاستخراج بيألّف قيم وكل أمثلة الـ few-shot متملية على الآخر
Add partial records, vague values kept as written, absent ones marked not specified; let it admit uncertaintyزوّد سجلات ناقصة، وقيم مبهمة متسابة زي ما اتكتبت، واللي مش موجود يتكتب عليه «غير محدد»؛ واسمحله يقول إنه مش متأكد
The example list grows with every misclassified edge case
قايمة الأمثلة بتكبر مع كل حالة حدّية اتصنّفت غلط
Use a few diverse, canonical examples, each showing why it got its labelخليك في شوية أمثلة نموذجية متنوعة، كل واحد بيوضّح ليه أخد التصنيف بتاعه
Adding examples made long or non-English inputs regress
بعد ما زوّدت أمثلة، المدخلات الطويلة أو اللي مش بالإنجليزي بقت تطلع أوحش
Diversify them across length, language, structure and edge cases; don't delete or duplicate themنوّع الأمثلة في الطول واللغة والبنية والحالات الحدّية؛ متشيلهاش ومتكررهاش
4.3 Enforce structured output using tool use and JSON schemas
Malformed JSON breaks the parser
JSON بايظ بيكسر الـ parser
tool_use with a JSON schematool_use مع JSON schema
Document type unknown, several schemas
نوع المستند مش معروف وفيه كذا schema
tool_choice: "any"tool_choice: "any"
One extraction must run before enrichment
استخراج معيّن لازم يشتغل قبل الإثراء
Force that tool by name with tool_choice; any lets Claude pick a different toolاجبر الأداة دي باسمها في tool_choice؛ any بيسيب Claude يختار أداة تانية
Claude must reason in text before the extraction call
لازم Claude يكتب تفكيره كنص قبل استدعاء أداة الاستخراج
Use auto with an instruction, accepting the call isn't guaranteed; forcing allows no text or thinking firstاستخدم auto مع تعليمات واقبل إن الاستدعاء مبقاش مضمون؛ الإجبار مبيطلّعش أي نص أو تفكير قبله
The model invents values for missing data
الموديل بيألّف قيم لبيانات مش موجودة
Make those fields optional / nullable; a required field pushes it to invent oneخلّي الحقول دي optional / nullable؛ الحقل الـ required بيزقّه يألّف قيمة
A value fits no enum category
قيمة مش داخلة في أي اختيار من الـ enum
"other" plus a detail string; "unclear" for ambiguous cases"other" ومعاها نص بالتفاصيل؛ و"unclear" للحالات الملخبطة
4.4 Implement validation, retry, and feedback loops for extraction quality
Schema-valid JSON, but totals don't add up or a value is misplaced
JSON مطابق للـ schema بس الإجماليات مش مظبوطة أو فيه قيمة في حقل غلط
Semantic validation in your code (calculated_total vs stated_total), not a stricter schema, more examples or temperature 0تحقق من المعنى في الكود بتاعك (calculated_total قصاد stated_total)، مش schema أشد ولا أمثلة أكتر ولا temperature 0
Validation failed: retry?
التحقق فشل: أعيد؟
Yes for format or structure errors; no if the information isn't in the sourceأيوه لو الغلط في الشكل أو الهيكل؛ لأ لو المعلومة مش موجودة في المصدر أصلاً
Retries keep producing the same error
الإعادة بتطلّع نفس الغلط كل مرة
Send the specific validation errors with the original document and the failed extractionابعت أخطاء التحقق بالظبط ومعاها المستند الأصلي والاستخراج اللي فشل
A required field stays empty through retries; the source lacks the value
حقل required فاضل فاضي بعد كذا إعادة والمصدر مفيهوش القيمة
Stop retrying (a bigger model won't help): make it nullable and escalate to a person or supply the missing documentبطّل إعادة (موديل أكبر مش هيفيد): خلّي الحقل nullable وصعّد لشخص أو هات المستند الناقص
You need to know where false positives come from
عايز تعرف الإنذارات الكاذبة جاية منين
A detected_pattern field logged with each dismissal, not dismissal_reason or a confidence scoreحقل detected_pattern يتسجّل مع كل رفض، مش dismissal_reason ولا درجة ثقة
4.5 Design efficient batch processing strategies
A pre-merge check a developer is waiting for
فحص قبل الـ merge والمطوّر مستنيه
The synchronous API; batches have no latency guarantee, however fast they usually finishالـ API العادي (synchronous)؛ الـ batches مفيهاش ضمان وقت، مهما كانت بتخلص بسرعة عادةً
Overnight or weekly analysis
تحليل بالليل أو كل أسبوع
Message Batches API: 50% cheaper, up to 24 hours, no latency guaranteeMessage Batches API: أرخص 50%، لحد 24 ساعة، ومن غير ضمان وقت
A workflow needs a multi-turn loop that runs your own tools
الشغل محتاج حلقة على كذا دور بتشغّل أدواتك إنت
Keep it on the synchronous API; batch only single-pass steps such as triageخليها على الـ API العادي (synchronous)؛ وحط في الـ batch الخطوات اللي بتخلص في لفة واحدة بس زي الفرز
Matching batch results to their requests
ربط نتايج الـ batch بالطلبات بتاعتها
Join on custom_id; .jsonl result lines come in no guaranteed orderاربطها بالـ custom_id؛ سطور النتايج في .jsonl مش مضمون إنها ماشية بالترتيب
Part of a batch failed
جزء من الـ batch فشل
Resubmit only the failures by custom_id in a new batch, each with its fix (e.g. split oversized documents)ابعت الفاشل بس تاني بالـ custom_id في batch جديدة، كل واحد بتصليحه (زي إنك تقسّم المستندات الكبيرة)
Choosing custom_id values for batch requests
اختيار قيم custom_id لطلبات الـ batch
Unique in the batch; 1 to 64 letters, digits, hyphens or underscores, e.g. doc-2026-report_finalمش متكرر جوه الـ batch؛ من 1 لـ 64 حرف، كلها حروف أو أرقام أو شُرَط أو شُرَط سفلية، زي doc-2026-report_final
Sizing batches for a large job (e.g. 150,000 invoices)
تحديد حجم الـ batches لشغل كبير (زي 150,000 فاتورة)
Up to 100,000 requests or 256 MB per batch; no hourly cap, and Messages API rate limits are untouchedلحد 100,000 طلب أو 256 MB في الـ batch الواحدة؛ مفيش حد بالساعة، وحدود معدل الـ Messages API مش بتتأثر
4.6 Design multi-instance and multi-pass review architectures
Reviewing code the same session or subagent wrote
مراجعة كود كتبته نفس الجلسة أو نفس الوكيل الفرعي
An independent instance with a fresh context (same model is fine), not the resumed writer or extended thinkingنسخة مراجعة مستقلة بسياق جديد (نفس الموديل مفيش مشكلة)، مش الكاتب بعد ما تكمّل جلسته ولا extended thinking
A 14-file PR review is shallow and contradictory
مراجعة PR فيه 14 ملف طالعة سطحية ومتناقضة
One pass per file, plus a cross-file integration passجولة لكل ملف، وجولة تانية للربط بين الملفات
Two per-file passes give conflicting recommendations
جولتين لملفين مختلفين طالعين بتوصيات متعارضة
Add a cross-file integration pass that reads both files side by side; don't ask the original authorزوّد جولة ربط بين الملفات تقرا الملفين جنب بعض؛ متسألش الكاتب الأصلي
Where to filter noise in a multi-pass review
الدوشة في مراجعة على كذا جولة تتصفّى فين
In a separate verification pass; the finding pass reports every issue with confidence and severityفي جولة تحقق منفصلة؛ جولة الاكتشاف تبلّغ عن كل مشكلة ومعاها درجة الثقة والخطورة
PR findings must be independently verified, and the team accepts the wait
ملاحظات الـ PR لازم تتأكد بشكل مستقل والفريق مش فارق معاه الانتظار
Claude Code's Code Review: about 20 minutes, billed in usage credits; comments only, never approves or blocksCode Review بتاع Claude Code: حوالي 20 دقيقة وبيتحاسب من رصيد الاستخدام؛ بيعلّق بس، عمره ما بيوافق أو بيوقف
Too few human reviewers
المراجعين البشريين قليلين
Confidence per finding, calibrated on a labeled set, to prioritize their workConfidence لكل ملاحظة متعايرة على بيانات متعلّم عليها، عشان ترتّب شغلهم
