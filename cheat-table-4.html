Domain 4

Prompt Engineering & Structured Output

20% of exam

Make Claude's output accurate, consistent, machine-readable and production-ready.

4.1

Precision & false positives

Reduce false positives and improve accuracy.

Do

  • Use explicit detection criteria.
  • Define clear rules (with a concrete example) for each severity level.
  • Add examples of acceptable patterns that should NOT be reported.
  • If a category has repeated false positives, disable it temporarily, refine it and test.

Avoid

  • Vague or general instructions ("be conservative").
  • Inconsistent severity definitions.
  • Relying on high confidence alone, without clear criteria and evidence.
4.2

Few-shot prompting

Use examples to guide Claude's behaviour.

How it helps

  • Provide representative input/output examples.
  • Include ambiguous cases and edge cases.
  • Show correct labels, especially for easily confused categories.

Example

Input

Password stored in plain text

{
  "category": "Security"
}

Remember

Examples teach Claude the pattern better than instructions alone.

4.3

Structured output

Consistent, machine-readable results.

JSON

The actual output format.

{
  "severity": "high",
  "file": "LoginViewModel.swift",
  "line": 42,
  "message": "Missing error handling"
}

JSON Schema

Defines required fields, types and constraints.

{
  "type": "object",
  "required": ["severity",
    "file", "line", "message"]
}

Validation levels

  1. Schema validationChecks structure, required fields and data types.
  2. Semantic validationChecks the finding is actually correct and matches the code and criteria.

Valid structure ≠ valid content

JSON can be schema-valid and still contain an incorrect finding.

4.4

Validation, retry & feedback

Handle invalid outputs reliably.

  1. ValidateCheck the output against the schema and rules.
  2. Provide specific feedbackSend Claude the exact validation errors.
  3. Retry with a limitAllow a limited number of correction attempts.
  4. Handle failureIf retries run out, fail gracefully and take an appropriate action.

Example error feedback

Validation errors:

  • severity must be one of: critical, high, medium, low
  • line must be an integer

Correct the output to satisfy the schema.

Works well for

  • Invalid JSON
  • Missing required fields
  • Schema violations

May not be enough for

  • Incorrect business logic
  • Issues that need deeper reasoning
4.5

Message Batches

Process many requests efficiently.

Use when

  • Large numbers of independent requests.
  • Results aren't needed immediately.
  • Reducing API cost is a priority (50% of standard price).

Avoid when

  • A response is needed immediately (a user is waiting).
  • The next step depends on the current result.
  • A tight deadline needs synchronous processing (batches only promise ≤ 24 h).

Example

Good fitClassify 5,000 support tickets overnight.
Not a good fitReview a PR while the developer waits for results.
4.6

Multi-instance & multi-pass review

Improve review quality and coverage.

Multi-instance (independent review)

Instance AGenerates code
→
Instance BReviews code (independent context)
  • Use a separate review instance to reduce bias from the generation session's context.

Multi-pass review

Break complex reviews into focused passes.

Pass 1Correctness (bugs, logic)
→
Pass 2Security (vulnerabilities)
→
Pass 3Performance (expensive ops)

Key takeaways

  1. Be explicit and provide clear criteria.
  2. Use examples to guide Claude's behaviour.
  3. Enforce structured outputs and validate them.
  4. Use actionable feedback with limited retries.
  5. Choose the right processing method (sync vs batches).
  6. Use independent instances and multi-pass reviews for higher quality.

Do vs don't

Do

  • Use clear, specific prompts.
  • Provide representative examples.
  • Define structured outputs with JSON Schema.
  • Validate and give specific feedback.
  • Batch high-volume, non-urgent tasks.
  • Use separate instances and multi-pass reviews.

Don't

  • Use vague instructions.
  • Rely on high confidence alone.
  • Assume schema validity means correctness.
  • Retry without feedback.
  • Use batches for time-critical requests.
  • Review in the same session that generated the code.
