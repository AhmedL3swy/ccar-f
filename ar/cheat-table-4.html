المجال 4

هندسة البرومبت والمخرجات المنظّمة

20% من الامتحان

خلي مخرجات Claude دقيقة، ثابتة، البرامج تقدر تقراها، وجاهزة للاستخدام الفعلي.

4.1

الدقة والإنذارات الكاذبة

قلّل الإنذارات الكاذبة وزوّد الدقة.

اعمل

  • استخدم معايير صريحة للاكتشاف.
  • حدد قواعد واضحة (بمثال حقيقي) لكل درجة خطورة.
  • ضيف أمثلة لأنماط مقبولة مينفعش تتبلّغ كمشكلة.
  • لو فيه فئة بتطلّع إنذارات كاذبة كتير، اقفلها مؤقتًا، ظبّطها، وجرّبها تاني.

ابعد عن

  • تعليمات مبهمة أو عامة (زي "خليك حذر").
  • تعريفات درجات الخطورة مش ثابتة.
  • إنك تعتمد على الثقة العالية لوحدها، من غير معايير واضحة ودليل.
4.2

البرومبت بالأمثلة التوضيحية

استخدم أمثلة عشان توجّه Claude.

بيفيد في إيه

  • إدّي أمثلة مدخلات ومخرجات بتمثّل الحالات الحقيقية.
  • حط الحالات المش واضحة والحالات الحدّية.
  • ورّيه التصنيفات الصح، خصوصًا للفئات اللي سهل تتلخبط في بعض.

مثال

المدخلات

Password stored in plain text

{
  "category": "Security"
}

افتكر

الأمثلة بتعلّم Claude النمط أحسن من التعليمات لوحدها.

4.3

المخرجات المنظّمة

نتايج شكلها ثابت والبرامج تقدر تقراها.

JSON

ده شكل المخرجات الفعلي.

{
  "severity": "high",
  "file": "LoginViewModel.swift",
  "line": 42,
  "message": "Missing error handling"
}

مخطط JSON

بيحدد الحقول المطلوبة، الأنواع، والقيود.

{
  "type": "object",
  "required": ["severity",
    "file", "line", "message"]
}

مستويات التحقق

  1. التحقق من المخططبيتأكد من الهيكل، الحقول المطلوبة، وأنواع البيانات.
  2. التحقق من المعنىبيتأكد إن الملاحظة صح فعلًا وماشية مع الكود والمعايير.

هيكل سليم ≠ محتوى سليم

الـ JSON ممكن يكون ماشي مع المخطط تمام وبرضه فيه ملاحظة غلط.

4.4

التحقق، إعادة المحاولة، ورسالة التصحيح

اتعامل مع المخرجات اللي مش سليمة بطريقة تعتمد عليها.

  1. اتحقققارن المخرجات بالمخطط والقواعد.
  2. ابعت رسالة تصحيح محددةابعت لـ Claude أخطاء التحقق بالظبط.
  3. أعد المحاولة بحد أقصىاسمح بعدد محدود من محاولات التصليح.
  4. اتعامل مع الفشللو المحاولات خلصت، افشل بهدوء من غير ما توقّع النظام وخد الإجراء المناسب.

مثال لرسالة التصحيح

أخطاء التحقق:

  • severity لازم تكون واحدة من: critical، high، medium، low
  • line لازم يكون رقم صحيح

صلّح المخرجات عشان تمشي مع المخطط.

بينفع مع

  • JSON مش سليم
  • حقول مطلوبة ناقصة
  • مخالفات للمخطط

ممكن ميكفيش في

  • منطق شغل غلط
  • مشاكل محتاجة تفكير أعمق
4.5

الـ Message Batches API

عالج طلبات كتير بكفاءة.

استخدمها لما

  • يكون عندك طلبات كتير مستقلة عن بعض.
  • النتايج مش مطلوبة على طول.
  • تقليل تكلفة الـ API مهم (50% من السعر العادي).

ابعد عنها لما

  • الرد مطلوب حالًا (فيه مستخدم مستني).
  • الخطوة الجاية معتمدة على النتيجة الحالية.
  • فيه ميعاد تسليم ضيق محتاج معالجة فورية (الدفعات بتضمن بس ≤ 24 ساعة).

مثال

مناسبةتصنّف 5,000 تذكرة دعم فني بالليل.
مش مناسبةمراجعة PR والمطوّر قاعد مستني النتيجة.
4.6

المراجعة بأكتر من نسخة وعلى أكتر من جولة

حسّن جودة المراجعة وتغطيتها.

نسخ متعددة (مراجعة مستقلة)

النسخة أبتكتب الكود
→
النسخة ببتراجع الكود (سياق مستقل)
  • استخدم نسخة منفصلة للمراجعة عشان تقلل التحيّز اللي جاي من سياق الجلسة اللي كتبت الكود.

المراجعة على كذا جولة

قسّم المراجعات المعقدة لجولات، كل جولة مركّزة على حاجة.

جولة 1الصحة (الغلطات، المنطق)
→
جولة 2الأمان (الثغرات)
→
جولة 3الأداء (العمليات التقيلة)

الخلاصة

  1. خليك صريح وإدّي معايير واضحة.
  2. استخدم أمثلة عشان توجّه Claude.
  3. افرض مخرجات منظّمة واتحقق منها.
  4. ابعت رسالة تصحيح ينفع يتصرف على أساسها، مع عدد محاولات محدود.
  5. اختار طريقة المعالجة الصح (فورية ولا دفعات).
  6. استخدم نسخ مستقلة ومراجعات على كذا جولة عشان الجودة تبقى أعلى.

اعمل ومتعملش

اعمل

  • استخدم برومبتات واضحة ومحددة.
  • إدّي أمثلة بتمثّل الحالات الحقيقية.
  • حدد المخرجات المنظّمة بمخطط JSON.
  • اتحقق وابعت رسالة تصحيح محددة.
  • حط المهام الكتير اللي مش مستعجلة في دفعة.
  • استخدم نسخ منفصلة ومراجعات على كذا جولة.

متعملش

  • متستخدمش تعليمات مبهمة.
  • متعتمدش على الثقة العالية لوحدها.
  • متفترضش إن مطابقة المخطط معناها إن الكلام صح.
  • متعيدش المحاولة من غير رسالة تصحيح.
  • متستخدمش الدفعات للطلبات المستعجلة.
  • متراجعش في نفس الجلسة اللي كتبت الكود.
